# Vast.ai vs RunPod: on-demand GPU platforms for short scripted YOLO training runs (state as of 2026-11-09)

> Method and date notes. Docs were read as raw markdown (docs.vast.ai and docs.runpod.io `*.md` / `llms-full.txt`) on 2026-11-09. Vast prices come from a live, unauthenticated POST to the public marketplace endpoint `https://console.vast.ai/api/v0/bundles/` on 2026-11-09 (my own query, single-GPU offers; `dph_total` includes a default 5 GiB of storage). RunPod prices come from the pricing page stamped "Updated November 4, 2026". Tags: [DOC] = official documentation, [LIVE] = live API/marketplace data, [USER] = user report/issue thread, [3P] = third-party documentation. I never rented an instance, so no runtime behaviour was tested directly.

## 1. CLI/SDK/REST: search, create, poll, startup script, destroy; can an instance destroy itself?

### Takeaway
Both platforms can be driven end to end from a script. Vast has a real offer-search step (you pick a specific host) and a per-instance restricted key (`CONTAINER_API_KEY`) that is documented to stop or destroy only that instance, so in-container self-destruct is documented. RunPod has no offer search (you request one GPU type and retry yourself) and injects a "Pod-scoped" `RUNPOD_API_KEY` plus a preinstalled `runpodctl`; self-stop from inside is shown in the docs, while self-terminate from inside is only supported by a community post. RunPod REST v1 is retired on 2026-11-15, so many older snippets break.

### Cited Findings

**Vast.ai: search**
- [DOC] CLI: `vastai search offers '<query>' [-t on-demand|reserved|bid] [-i] [-o 'dph+'] [--limit N]`. Default query is `external=false rentable=true verified=true` (`-n` disables it); `-i`/`-b` means interruptible (bid) pricing; `--storage` sets the GiB used for price calculation (default 5). String values replace spaces with underscores (`gpu_name=RTX_4090`). Example from the docs: `vastai search offers 'reliability > 0.98 num_gpus=1 gpu_name=RTX_3090 rented=False'`. Fields include `dph`, `reliability`, `verified`, `datacenter`, `inet_down`, `inet_down_cost` ($/GB), `inet_up_cost`, `storage_cost` ($/GB/month), `disk_space`, `duration` (max rental days), `direct_port_count`, `cuda_vers`, `min_bid`, `vms_enabled`, `geolocation` — [search-offers CLI ref](https://docs.vast.ai/cli/reference/search-offers.md)
- [DOC] REST: `POST https://console.vast.ai/api/v0/bundles/` with `Authorization: Bearer $VAST_API_KEY` and JSON like `{"verified":{"eq":true},"rentable":{"eq":true},"gpu_name":{"eq":"RTX 4090"},"num_gpus":{"eq":1},"direct_port_count":{"gte":1},"order":[["dlperf_per_dphtotal","desc"]],"type":"on-demand","limit":5}`; operators eq/neq/gt/lt/gte/lte/in/notin; response has `offers[]` — [API hello world (in llms-full)](https://docs.vast.ai/llms-full.txt), [search offers API ref](https://docs.vast.ai/api-reference/search/search-offers.md). Doc inconsistency: hello-world uses `"type":"on-demand"` while the OpenAPI enum is `ondemand|bid|reserved`; in my 2026-11-09 test `"ondemand"` and `"bid"` both returned offers [LIVE] — [bundles endpoint](https://console.vast.ai/api/v0/bundles/). The endpoint answered with no API key at all in my test [LIVE].
- [DOC] OpenAPI quirk list: `gpu_ram` is GB in the CLI but MB in REST; create returns `new_contract` (not `id`) as the instance ID; SSH keys must be registered before creation — [search offers API ref](https://docs.vast.ai/api-reference/search/search-offers.md)

**Vast.ai: create, startup script, poll, destroy**
- [DOC] CLI create: `vastai create instance OFFER_ID --image pytorch/pytorch --disk 40 --env '-e KEY=VAL -p 8081:8081' --ssh --direct --onstart-cmd "..."`; interruptible: add `--bid_price 0.1`; `--cancel-unavail` returns an error instead of creating a stopped instance if scheduling fails; `--args ...` (must be last) launches in "args/entrypoint mode" without ssh/jupyter injection; returns `{'success': True, 'new_contract': 7835610}`. Each offer ID can create only one instance — [create-instance CLI ref](https://docs.vast.ai/cli/reference/create-instance.md)
- [DOC] REST create: `PUT https://console.vast.ai/api/v0/asks/{offer_id}/` body fields `image` (required), `disk` (GB), `onstart`, `env` (docker-flag string `"-e A=B -p 8000:8000"`), `runtype` (ssh|jupyter|args|ssh_proxy|ssh_direct|...), `price` (bid $/h, only for interruptible, 0.001-128), `target_state`, `cancel_unavail`, `label`, `template_hash_id`, `args`/`args_str`, `vm`. Response includes `new_contract` and `instance_api_key` — [create-instance API ref](https://docs.vast.ai/api-reference/instances/create-instance.md), [hello world](https://docs.vast.ai/llms-full.txt)
- [DOC] Launch modes: in SSH/Jupyter modes the image's original ENTRYPOINT is replaced and your command goes in `onstart` (script also at `/root/onstart.sh`, runs on every container start); in entrypoint/args mode "your command runs automatically on startup". Env vars from `-e` are visible to onstart but not to SSH sessions unless written to `/etc/environment` (`env | grep _ >> /etc/environment`) — [docker-environment](https://docs.vast.ai/guides/instances/docker-environment.md), [instances FAQ](https://docs.vast.ai/guides/reference/faq/instances.md)
- [DOC] onstart size limit conflicts: CLI quickstart says `--onstart-cmd` is limited to 16KB; OpenAPI header says the `onstart` field is limited to 4048 characters (gzip+base64 for longer) — [CLI quickstart (llms-full)](https://docs.vast.ai/llms-full.txt), [create-instance API ref](https://docs.vast.ai/api-reference/instances/create-instance.md)
- [DOC] Poll: `GET /api/v0/instances/{id}/` → `actual_status`: `null` (provisioning) → `"loading"` (Docker image downloading) → `"running"`. `exited` (container crashed), `unknown` (no host heartbeat) or `offline` will never reach `running`; script must time out and destroy. Poll every 10 s; boot typically 1-5 min depending on image size. CLI: `vastai show instance ID --raw`. Instance stuck in `loading` >15 min "may have failed silently" - destroy and try another offer — [hello world](https://docs.vast.ai/llms-full.txt), [show-instances API](https://docs.vast.ai/api-reference/instances/show-instances.md)
- [DOC] Destroy: `vastai destroy instance ID` or `DELETE /api/v0/instances/{id}/` (irreversible, deletes data). Stop: `vastai stop instance ID` or `PUT .../instances/{id}/ {"state":"stopped"}` - compute billing stops, disk billing continues — [destroy CLI](https://docs.vast.ai/cli/reference/destroy-instance.md), [hello world](https://docs.vast.ai/llms-full.txt)
- [DOC] Python SDK exists: `pip install vastai`, `from vastai import VastAI`, with `search_offers`, `create_instance`, `show_instance(s)`, `destroy_instance(s)` — [SDK reference index](https://docs.vast.ai/llms.txt)

**Vast.ai: self-destruct from inside the container**
- [DOC] Every instance gets predefined env vars `CONTAINER_API_KEY` ("per-instance API key for CLI commands from inside the container") and `CONTAINER_ID`; the create response's `instance_api_key` "is a restricted key ... it can only start, stop, or destroy that specific instance". In-container recipe: `curl -fsSL https://vast.ai/install.sh | bash` then `vastai destroy instance $CONTAINER_ID` (add `--api-key $CONTAINER_API_KEY` if not auto-configured); "You can also stop or destroy the instance from within". If the vars are missing in an SSH session, export them via `/etc/environment`; the key can be regenerated from `~/.ssh/authorized_keys` md5 + `VAST_CONTAINERLABEL` md5 into `~/.vast_api_key` — [docker-environment](https://docs.vast.ai/guides/instances/docker-environment.md), [instances FAQ](https://docs.vast.ai/guides/reference/faq/instances.md)
- [DOC] Main user keys are full-access by default; for automation Vast recommends scoped keys created via `vastai create api-key` — [API keys guide](https://docs.vast.ai/guides/reference/api-keys.md)
- [DOC] Account-level env vars set in Settings are injected into every container (a place for R2 credentials, subject to the host-trust caveat in section 4) — [docker-environment](https://docs.vast.ai/guides/instances/docker-environment.md)

**RunPod: create, poll, destroy**
- [DOC] REST API v2 base URL `https://api.runpod.io/v2`, Bearer API key. REST v1 (`https://rest.runpod.io/v1`) and GraphQL are deprecated; "REST API v1 ... will be retired on November 15, 2026" — [API v2 overview](https://docs.runpod.io/api-reference-v2/overview.md), [migrate from v1](https://docs.runpod.io/api-reference-v2/migrate-from-v1.md). Vast's own RunPod migration guide still shows v1 URLs, i.e. snippets in the wild are stale — [Vast migration guide](https://docs.vast.ai/examples/migrations/runpod-to-vast)
- [DOC] Create (CLI): `runpodctl pod create --image "runpod/pytorch:..." --gpu-id "NVIDIA GeForce RTX 4090" --container-disk-in-gb 30 --cloud-type COMMUNITY --env '{"KEY":"v"}' --docker-args "..."` (also `--volume-in-gb`, `--network-volume-id`, `--data-center-ids`, `--min-cuda-version`, `--ports`, `--template-id`; default `--cloud-type SECURE`, default container disk 20 GB) — [runpodctl pod reference](https://docs.runpod.io/runpodctl/reference/runpodctl-pod.md)
- [DOC] Create (REST v2): `POST /v2/pods` body e.g. `{"name":"x","image":"...","gpu":{"id":"NVIDIA GeForce RTX 4090","count":1,"minRamPerGpu":32,"minVcpuCountPerGpu":8},"disk":50,"cloud":"COMMUNITY"}`; `cloud` defaults to `SECURE`; `args` is "the container's command, as a single raw string" (bare string = CMD; or JSON `{"entrypoint":["/bin/bash","-c"],"cmd":["python -u main.py"]}`); `env` is a `{"K":"v"}` object; `disk` = container disk GB (ephemeral); in v2 a pod without `mounts` has no persistent storage — [create-a-pod API](https://docs.runpod.io/api-reference-v2/pods/create-a-pod.md), [migrate from v1](https://docs.runpod.io/api-reference-v2/migrate-from-v1.md)
- [DOC] There is no "search offers": "This endpoint places one specific GPU type. It does not search for capacity ... and it does not fall back to a different GPU". You check availability (HIGH/MEDIUM/LOW/NONE) via `GET /v2/catalog/gpu-types` / datacenters and retry in your own loop; the catalog needs a bearer token (HTTP 401 unauthenticated in my test) — [create-a-pod API](https://docs.runpod.io/api-reference-v2/pods/create-a-pod.md), [migrate from v1](https://docs.runpod.io/api-reference-v2/migrate-from-v1.md)
- [DOC] Poll: `GET /v2/pods/{id}`; status enum `PROVISIONING, STARTING, RUNNING, EXITED, ERROR, TERMINATED`; handle `ERROR` in loops. CLI `runpodctl pod get <id>`, `runpodctl pod list --all`. Default `pod list` shows running and error pods "because they still exist and may still incur charges" — [create-a-pod API](https://docs.runpod.io/api-reference-v2/pods/create-a-pod.md), [runpodctl pod](https://docs.runpod.io/runpodctl/reference/runpodctl-pod.md)
- [DOC] Stop: `runpodctl pod stop ID` / `POST /v2/pods/{id}/action {"action":"stop"}` (actions: start, stop, restart, terminate). Terminate: `runpodctl pod delete ID` / `DELETE /v2/pods/{id}` (204). Terminate permanently deletes everything not on a network volume — [manage pods](https://docs.runpod.io/pods/manage-pods.md), [terminate API](https://docs.runpod.io/api-reference-v2/pods/terminate-a-pod.md)
- [DOC] Python package `runpod`: "API wrapper functions such as `runpod.create_pod` and `runpod.get_pods` still work" in the 2.0 line (2.0 was still at release-candidate in the doc text) — [SDK migrate page](https://docs.runpod.io/sdk/migrate-from-flash)
- [DOC] API is rate limited per minute/hour/day with `RateLimit` headers and 429s — [API v2 overview](https://docs.runpod.io/api-reference-v2/overview.md)

**RunPod: self-destruct from inside the pod**
- [DOC] Runpod-set env vars include `RUNPOD_POD_ID` and `RUNPOD_API_KEY` ("Pod-scoped API key"); "Every Pod comes preinstalled with `runpodctl` and a Pod-scoped API key" — [env vars](https://docs.runpod.io/pods/templates/environment-variables.md), [runpodctl overview](https://docs.runpod.io/runpodctl/overview.md)
- [DOC] The manage-pods page shows running the CLI against `$RUNPOD_POD_ID`, including a scheduled stop from inside: `sleep 2h; runpodctl pod stop $RUNPOD_POD_ID &`; terminate is `runpodctl pod delete $RUNPOD_POD_ID` — [manage pods](https://docs.runpod.io/pods/manage-pods.md). The doc does not say what the Pod-scoped key may do beyond that.
- [USER] A 2024-era community thread ("Possible to terminate pod from within the pod?") is summarised (search snippet only; the page returned HTTP 429/anti-bot to my fetches) as: use `runpodctl remove pod $RUNPOD_POD_ID` from inside; the poster said it was untested whether the injected scoped key suffices; another user reported a `sleep 1h; runpodctl stop pod ... && runpodctl remove pod ...` chain left the pod only "Exited", not removed — [thread](https://www.answeroverflow.com/m/1267200524181180427)
- [DOC] Stop is not enough to stop all billing: stopped pods still pay volume-disk storage (section 2) — [manage pods](https://docs.runpod.io/pods/manage-pods.md)

### Inferences
- Minimal Vast flow: search (`reliability>0.98 verified`, price-sorted) → PUT create with `image`, `disk`, `env` (R2 credentials, run id), `onstart` that runs `train.py` then `vastai destroy instance $CONTAINER_ID`, plus an outside watchdog that destroys after a hard deadline. This composition follows from the docs but no doc shows the combined script; the doc only says to "test with start first".
- Because Vast's `args`/entrypoint mode ends the container when the command exits (`exited` status), and exited instances still bill disk until destroyed, the training script should call destroy itself rather than just exit.
- For RunPod, safest is a stop-gap pair: in-container `runpodctl pod delete $RUNPOD_POD_ID` after upload, plus an external deleter holding the main key, because the Pod-scoped key's permission to terminate is not documented.
- Anything written against `rest.runpod.io/v1` or GraphQL will stop working on 2026-11-15 (6 days after these notes), so use v2 or the `runpodctl` shipped in current images.

### Gaps
- No official end-to-end "train then self-destroy" example for either platform; the combination above is untested.
- Whether Vast's `CONTAINER_API_KEY` works as a Bearer key for REST `DELETE /instances/{id}/` (versus only through the CLI) is not stated; the CLI path is documented.
- RunPod Pod-scoped key permissions (can it terminate?) not documented in pages I read; community evidence is weak and dated 2024.
- What happens to billing on RunPod when the container's start command simply exits (pod goes `EXITED`; volume disk keeps billing, container disk does not per the pricing table) is inferred from the status enum and pricing page, not stated in one place.

## 2. Prices (late 2026) and billing rules

### Takeaway
On a 2026-11-09 snapshot, Vast single-GPU consumer cards are cheaper than RunPod on-demand for 3060-class through 4090 hosts you would actually trust (e.g. reliable verified RTX 4090 about $0.46-0.55/h vs RunPod Community $0.34 and Secure $0.89), and Vast alone has an interruptible tier (typically 25-45% below on-demand); RunPod retired Spot Pods. Both bill per second. Vast storage bills until you destroy, and bandwidth is host-set and bidirectional; RunPod has no ingress/egress fees.

**Vast.ai billing rules [DOC]**
- GPU compute billed per second while running; "Interruptible ... often 50%+ cheaper than on-demand" and FAQ says "Saves 50-80%" (my live data shows ~25-45% below on-demand medians for these cards) — [pricing](https://docs.vast.ai/guides/instances/pricing.md), [rental types FAQ](https://docs.vast.ai/guides/reference/faq/rental-types.md)
- Storage billed every second the instance exists (not offline), in any state; "Stopping an instance does not avoid storage costs"; stopped storage rate "typically higher" — [billing](https://docs.vast.ai/guides/reference/billing.md), [pricing](https://docs.vast.ai/guides/instances/pricing.md)
- Bandwidth: per byte sent or received, upload and download, regardless of instance state; "Providers set rates for bandwidth ... both inbound and outbound traffic are billed, so pulling large models or datasets counts" — [billing](https://docs.vast.ai/guides/reference/billing.md), [Vast migration guide](https://docs.vast.ai/examples/migrations/runpod-to-vast)
- No minimum billing increment documented; "If I rent a server and delete it after 10 minutes ... You will only be charged for the 10 minutes". Not charged while status is "Loading". Balance updates every few seconds — [billing](https://docs.vast.ai/guides/reference/billing.md)
- Prepaid credits; at $0 balance instances are stopped (not destroyed), with a grace buffer based on average daily spend; with a saved card the card is auto-charged, with no card instances/data are scheduled for deletion — [billing](https://docs.vast.ai/guides/reference/billing.md)
- Disk size is fixed at creation and cannot be changed — [instances FAQ](https://docs.vast.ai/guides/reference/faq/instances.md)

### Inferences
- Illustrative 2-hour run (compute + disk, computed from the figures above): Vast verified+reliable RTX 4090 about 2 x $0.46-0.55 = $0.92-1.10 plus bandwidth ($2.6-6.5/TB x a ~10-50 GB dataset is a few cents); RunPod Community 4090 2 x $0.34 = $0.68 plus about $0.005 for 20 GB container disk; RunPod Secure 4090 2 x $0.89 = $1.78. Interruptible Vast 4090 (verified, $0.27-0.35/h) is roughly as cheap as RunPod Community on-demand, with eviction risk.
- For small YOLO models (YOLOv8n/s/m fit in 8-12 GB), RTX 3060/3070/A4000 on Vast at $0.06-0.09/h are the cheapest per hour, but per-run cost depends on throughput; no benchmark was in scope.
- Vast's cheapest rows trade away reliability or bandwidth; the effective price to budget is the "reliable + verified + inet_down>=500" row, about 1.3-1.5x the headline minimum.

### Gaps
- No RunPod prices for 3060/3070/3080/4070/4080/A4000 (pricing page omits them; catalog endpoint requires an authenticated call). Serverless per-second rates for the "A4000/A4500/RTX 4000" pool are in section 6 only as a proxy.
- Vast's own `vast.ai/pricing` page loads prices dynamically and showed none in static fetch; live API figures above are my substitute.
- Vast storage price while stopped ("typically higher") not quantified in docs.

## 3. Container privileges: FUSE (rclone mount, s3fs, mountpoint-s3), CAP_SYS_ADMIN, --privileged, Vast VMs, RunPod Pods vs Serverless

### Takeaway
I could not confirm FUSE support on either platform's default containers, and I found affirmative evidence against privileged mode: dstack's docs list `privileged` as unsupported on both RunPod and Vast.ai, a SkyPilot issue shows `mknod /dev/fuse: operation not permitted` on RunPod, and Vast's docs describe instances as unprivileged containers that only accept `-e/-h/-p/--shm-size` options. Vast's VM (KVM) instance type is the only documented route to FUSE-like needs ("Mount remote drives with rclone or similar"). Plan on `rclone copy`/`sync` or `aws s3`/`boto3` instead of mounting.

### Cited Findings
- [DOC] Vast: "Clients are isolated in unprivileged Docker containers" with separate namespaces/cgroups — [Security FAQ](https://docs.vast.ai/guides/reference/faq/security)
- [DOC] Vast: settable docker options are env vars (`-e`), hostname (`-h`), ports (`-p`); the technical FAQ adds `--shm-size`. No documented `--device`, `--cap-add`, or `--privileged`. "Docker-in-Docker is disabled for security" — [docker-environment](https://docs.vast.ai/guides/instances/docker-environment.md), [technical FAQ](https://docs.vast.ai/guides/reference/faq/technical.md)
- [DOC] Vast VMs: full Linux (KVM) with init manager (systemd) and ptrace; images only from `docker.io/vastai/kvm`; trade-offs: slower creation/boot, higher disk overhead, smaller machine selection, fewer templates, SSH launch mode only; cloud-copy for VMs only migrates whole VMs and only VM-to-VM; filter `vms_enabled=true` — [Virtual Machines](https://docs.vast.ai/guides/instances/virtual-machines.md)
- [DOC] Vast templates page says to use VM templates to "Run applications that require namespace support; Run more than one Docker container in an instance; Load kernel modules or run profiling jobs; Mount remote drives with rclone or similar" — [Templates intro](https://docs.vast.ai/guides/templates/introduction)
- [3P] dstack docs: "Privileged mode ... Not supported with daytona, lium, runpod, slurm, and vastai"; `docker: true` likewise unsupported on runpod and vastai; dstack blog: the privileged option "is only supported by VM-based backends. This does not include runpod, vastai, and kubernetes" — [dstack tasks docs](https://dstack.ai/docs/concepts/tasks/), [dstack DinD blog](https://dstack.ai/blog/docker-inside-containers/)
- [DOC] RunPod: "Docker Compose is not supported: Runpod runs Docker for you, so you cannot spin up your own Docker instance"; Pods are TCP/HTTP only, no UDP — [Pods overview](https://docs.runpod.io/pods/overview). No RunPod doc page I read mentions FUSE, `/dev/fuse`, `SYS_ADMIN` or `--privileged`.
- [USER] SkyPilot issue #8592 "[RunPod] FUSE mount fails inside Docker container - /dev/fuse: operation not permitted" (opened 2026-01-15, SkyPilot 0.11.x): errors `mknod /dev/fuse: operation not permitted` and `fuse device not found, try 'modprobe fuse' first`; installing the fuse package and `--privileged` did not help; maintainer: "The Fuse mounting is not fully tested on RunPod ... RunPod's virtualization differs"; community reply called it "a platform constraint" and suggested JuiceFS gateway mode (S3 endpoint, no FUSE); closed as "not planned" by stale bot on 2026-10-04 with no confirmed fix — [issue](https://github.com/skypilot-org/skypilot/issues/8592)
- [3P] Generic FUSE-in-container requirement is `/dev/fuse` plus `SYS_ADMIN` (or privileged), per rclone/Podman/Kubernetes threads surfaced by search; e.g. mounting a FUSE filesystem inside Docker needs privileged mode — [dstack issue #1403 (GCP, not Vast/RunPod)](https://github.com/dstackai/dstack/issues/1403)
- Searches for Vast.ai-specific FUSE reports (rclone mount, s3fs, goofys, sshfs, `/dev/fuse`) on forums/GitHub/Reddit returned nothing relevant; I found no first-hand Vast FUSE success or failure report.

### Inferences
- Treat FUSE as unavailable on Vast Docker instances and RunPod Pods unless tested on the specific machine; both platforms' evidence points to unprivileged containers (dstack lists both as no-privileged; Vast documents "unprivileged"). On Vast, hosts are independent operators, so a particular host could differ, but nothing documents a way to request `--device /dev/fuse`.
- Vast VM instances are the plausible path to rclone/s3fs mounts (documented use case, systemd, kernel modules), at the cost of slower boot, fewer offers and no cloud-copy; whether `/dev/fuse` and the `fuse` module are actually present in `vastai/kvm` images is not documented.
- A mount is not needed for a 10-minute to few-hour YOLO job: copy the dataset down with `rclone copy` / `aws s3 sync --endpoint-url https://<ACCOUNT_ID>.r2.cloudflarestorage.com` to local disk and upload `runs/` at the end.
- RunPod Serverless: no information found on privilege differences from Pods; same runtime family (container workers), so no reason to expect FUSE there.

### Gaps
- Not confirmed: existence of `/dev/fuse` in Vast Docker instances; whether `CAP_SYS_ADMIN` can ever be granted on either platform; Vast VM FUSE support; RunPod Serverless vs Pods privilege differences; any mountpoint-s3 or s3fs report on either platform.
- No empirical test (I did not rent machines); a 5-cent test (`ls -l /dev/fuse; rclone mount ...; capsh --print`) on each platform would settle it.

## 4. Reliability: host quality, Secure vs Community, interruptible eviction, startup time

### Takeaway
Vast reliability is per-host and filterable (reliability score, verified, datacenter), but it is a marketplace of independent operators; RunPod Secure is first-party/T3-T4 datacenter and Community is peer-to-peer, no longer taking new hosts. Vast interruptible instances are stopped when outbid with no documented grace signal (only an after-the-fact email/webhook); RunPod has no interruptible tier. Vast fresh image pulls can take 10-60 min; pre-cached base images and fast-downlink hosts cut this.

### Cited Findings

**Vast.ai**
- [DOC] Machine tiers: Unverified (new, untested; filtered out by default), Verified (passed Vast's internal tests; default search), Secure Cloud/Datacenter ("verified and confirmed to be in a certified datacenter ... TIER 2/3 rating or ISO 27001", blue label, "recommended for production") — [find and rent](https://docs.vast.ai/guides/instances/choosing/find-and-rent.md) (text in llms-full)
- [DOC] "Reliability score: historical uptime percentage. Look for 0.95+ for production workloads. If reliability is critical, filter for Secure Cloud machines only." Filter e.g. `reliability > 0.98`. Higher reliability "typically correlate[s] with higher prices" — [Vast migration guide](https://docs.vast.ai/examples/migrations/runpod-to-vast), [pricing](https://docs.vast.ai/guides/instances/pricing.md)
- [DOC] Security caveat: "Provider security varies significantly: Tier 4 datacenters have extensive ... security; Individual hosts may have less formal security"; Cloud Sync warns credentials are copied onto the host and to prefer Secure Cloud hosts — [Security FAQ](https://docs.vast.ai/guides/reference/faq/security), [Cloud Sync](https://docs.vast.ai/guides/instances/storage/cloud-sync.md)
- [DOC] On-demand "cannot be interrupted", yet `exited`/`unknown`/`offline` states exist, and notification types include "Instance offline: your instance went down because of a problem on the host machine", "Instance maintenance scheduled", "Upcoming instance downtime" — [rental types FAQ](https://docs.vast.ai/guides/reference/faq/rental-types.md), [notifications](https://docs.vast.ai/guides/reference/notifications.md)
- [DOC] Every offer has a maximum rental duration/"lifetime"; at expiry the instance is stopped and "may be deleted 48 hours after expiration" — [instances FAQ](https://docs.vast.ai/guides/reference/faq/instances.md), [instance types](https://docs.vast.ai/guides/instances/choosing/instance-types.md)
- [DOC] Interruptible: bidding; "May be paused if outbid or if on-demand requested"; priority: on-demand > higher bid > lower bid; when it loses: "Your instance is stopped (killing running processes) ... Instance may wait long to resume"; data preserved but instance not functional; resumes automatically when priority returns; "Save work frequently ... Implement checkpointing". No documented SIGTERM or grace period. Notifications `client:outbid` ("paused") and `Instance resumed` are emailed or sent by webhook (after the event) — [instance types](https://docs.vast.ai/guides/instances/choosing/instance-types.md), [rental types FAQ](https://docs.vast.ai/guides/reference/faq/rental-types.md), [notifications](https://docs.vast.ai/guides/reference/notifications.md)
- [DOC] Vast API troubleshooting: offers are dynamic; try the next offer if creation fails or use `cancel_unavail: true`; "My bid instance keeps getting interrupted": raise bid, pick lower-demand machines, or use on-demand — [creating instances with API (llms-full)](https://docs.vast.ai/llms-full.txt)
- [DOC] Startup: `loading` = Docker image downloading; boot typically 1-5 min "not counting Docker image pull time"; "cached images launch quickly, fresh pulls may take 10-60 minutes"; a ~15 GB Axolotl image "can take 30+ minutes" on slow links, so filter `inet_down >= 5000` (Mbps); >15 min in `loading` = destroy and retry. Ways to cut it: use Vast base images (pre-cached on many hosts, `github.com/vast-ai/base-image`, Docker Hub `vastai/*`), smaller images, build on a pre-cached base — [hello world](https://docs.vast.ai/llms-full.txt), [Vast migration guide](https://docs.vast.ai/examples/migrations/runpod-to-vast), [Axolotl guide](https://docs.vast.ai/examples/ai-ml-frameworks/axolotl-fine-tuning)
- [LIVE] Offer fields also show `inet_down` (Mbps) and `disk_bw` (MB/s); e.g. cheapest verified, reliability>=0.98, >=500 Mbps 4090 is in California at $0.459/h — [bundles endpoint](https://console.vast.ai/api/v0/bundles/)

**RunPod**
- [DOC] Secure Cloud: "T3/T4 data centers", high reliability; Community Cloud: "individual compute providers ... vetted, secure peer-to-peer system", reliability "Variable"; "Runpod is no longer accepting new hosts for Community Cloud. Existing Community Cloud resources remain available." Organization accounts can only deploy to Secure Cloud — [Pods overview](https://docs.runpod.io/pods/overview), [choose a pod](https://docs.runpod.io/pods/choose-a-pod), [get started](https://docs.runpod.io/get-started)
- [DOC] Community pods "aren't guaranteed a public IP" (SSH port may be unreachable) and public IPs may change on migration/restart — [runpodctl pod](https://docs.runpod.io/runpodctl/reference/runpodctl-pod.md), [expose ports](https://docs.runpod.io/pods/configuration/expose-ports)
- [DOC] Planned maintenance: email notice, pod time not billed. Unplanned outages: "may only be able to notify you after the outage has begun". If a pod "is interrupted, restarted, stopped, or terminated", data on container disk is lost; checkpoint "every hour to every few hours" — [maintenance and outages](https://docs.runpod.io/pods/maintenance-and-outages.md)
- [DOC] A running pod keeps its GPU exclusively; once stopped, the GPU can be taken by someone else, so restart may fail ("zero GPUs") and need beta "Pod migration" (new Pod ID/IP, copies only `/workspace` volume disk) — [pod migration](https://docs.runpod.io/pods/troubleshooting/pod-migration.md), [manage pods](https://docs.runpod.io/pods/manage-pods.md). Not relevant if you create fresh and terminate rather than stop/restart.
- [DOC] No interruptible/spot pods (retired, see section 2) — [Terraform 2.0 migration](https://docs.runpod.io/integrations/terraform/migration)
- [DOC] Startup: `initializing` = "no container reported ... image pull, container creation, or boot, which the platform does not distinguish"; no pull-time numbers or pre-cache guidance for Pods in the docs I read (FlashBoot/cached images are a Serverless feature) — [pods API status doc (llms-full)](https://docs.runpod.io/llms-full.txt)
- [USER] Trustpilot reviewers/forum users report Community-cloud restart failures ("Pod resume failed: There are not enough free GPUs on the host machine") and a RunPod docs thread titled zero GPUs on restart; only surfaced through a search snippet, anecdotal — [RunPod Trustpilot](https://se.trustpilot.com/review/runpod.io)

### Inferences
- Reasonable Vast filter for unattended runs: `verified=true reliability>0.98 inet_down>=500 direct_port_count>=1 duration>=<run hours>` on-demand, optionally `datacenter=true` for sensitive credentials at about 1.2-2x the price (live data).
- Because eviction on Vast gives no in-container warning, an interruptible run must checkpoint to R2 every N minutes, and the launcher/watchdog must detect `actual_status` flipping away from `running` and re-create elsewhere; Vast bid floor placement matters (a third-party guide suggests padding the min bid 20-50%, unverified).
- For jobs of 10 minutes to a few hours with a small image, startup is dominated by image pull on a fresh host; baking the YOLO environment on a pre-cached Vast base image (or a RunPod official `runpod/pytorch` template, which is likely cached though undocumented) is the main lever.

### Gaps
- No first-hand Reddit/Discord reports found on Vast interruptible resume wait times, eviction frequency, or host failure rates; no quantitative reliability data for either platform's Community/unverified tiers (the "reliability" number is Vast's own and not defined numerically beyond "historical uptime").
- No measured Pod startup times for RunPod; no statement on RunPod image caching for Pods.
- No evidence of any SIGTERM or warning signal on Vast interruptible eviction; absence is not proof.

## 5. Built-in cloud sync with S3-compatible endpoints such as Cloudflare R2

### Takeaway
Neither platform's built-in sync documents Cloudflare R2 or a custom S3 endpoint. Vast Cloud Sync supports Google Drive, Amazon S3, Backblaze, Dropbox and Hugging Face buckets (Docker instances only); RunPod Cloud Sync supports S3, GCS, Azure Blob, Backblaze B2 and Dropbox via a console button. Both are better replaced with `rclone`/`aws s3`/`boto3` run inside the container using your R2 endpoint and keys. RunPod has network volumes with their own S3 API, which is not an R2 integration.

### Cited Findings
- [DOC] Vast Cloud Sync = "Cloud Copy" button / `vastai cloud copy --src SRC --dst DST --instance ID --connection CONN_ID --transfer "Instance To Cloud"` (options `--dry-run`, `--size-only`, `--schedule HOURLY|DAILY|WEEKLY`), connections configured in Settings; providers: Google Drive, Amazon S3 (IAM user keys), Backblaze, Dropbox, Hugging Face (via S3-compatible Storage Buckets); "available on Docker-based instances only (not VM/KVM)"; credentials "temporarily copied onto your instance's host machine" so use scoped keys and Secure Cloud hosts — [Cloud Sync](https://docs.vast.ai/guides/instances/storage/cloud-sync.md), [cloud-copy CLI](https://docs.vast.ai/cli/reference/cloud-copy.md)
- [DOC] Cloudflare R2 is not in the Cloud Sync provider list. Vast's migration/Salad guides do name R2 as recommended object storage ("pull weights on boot ... Object storage (S3, R2, GCS)") and one says to use it "via Vast's built-in Cloud Sync" — an inconsistency with the Cloud Sync page; the Vast docs also say you can run "any other linux tools you can run inside the instance yourself (rclone, rsync, bittorent ...)" — [Vast migration guide](https://docs.vast.ai/examples/migrations/runpod-to-vast), [Salad migration (llms-full)](https://docs.vast.ai/llms-full.txt), [data movement](https://docs.vast.ai/guides/instances/storage/data-movement.md)
- [DOC] Vast has no cross-host network volume; local volumes are tied to one physical machine, so persistence across instances means object storage — [Vast migration guide](https://docs.vast.ai/examples/migrations/runpod-to-vast)
- [DOC] RunPod Cloud Sync: Pod page "Cloud Sync" button; providers Amazon S3 (access key + secret + AWS region + bucket path), Google Cloud Storage (service-account JSON), Azure Blob, Backblaze B2, Dropbox; not Google Drive; no R2 or custom-endpoint option is described — [Cloud Sync](https://docs.runpod.io/pods/storage/cloud-sync.md)
- [DOC] RunPod network volumes: persistent, Secure Cloud only ("Network volumes are only available for Pods in the Secure Cloud"), $0.07/GB/month; S3-compatible API for network volumes (use `aws s3 --endpoint-url <datacenter endpoint> --region <DC id>`), per-datacenter availability — [network volumes](https://docs.runpod.io/storage/network-volumes.md), [S3-compatible API](https://docs.runpod.io/storage/s3-api.md)
- [DOC] RunPod Serverless can attach external S3-compatible storage (AWS S3, MinIO, Backblaze B2, DigitalOcean Spaces "etc.") with your own credentials, mainly for payloads bigger than API limits — [Serverless storage](https://docs.runpod.io/serverless/storage/overview.md)
- [3P] R2 with rclone: remote type `s3`, provider `Cloudflare`, endpoint `https://<ACCOUNT_ID>.r2.cloudflarestorage.com` (seen only in a search snippet of Cloudflare's rclone page) — [Cloudflare R2 rclone docs](https://developers.cloudflare.com/r2/examples/rclone/)
- [DOC] RunPod Pods have no ingress/egress fees; Vast bills bandwidth per byte at host-set rates (section 2), so R2 downloads to Vast cost the host's inbound rate while R2-side egress is a separate matter — [pods pricing](https://docs.runpod.io/pods/pricing.md), [Vast billing](https://docs.vast.ai/guides/reference/billing.md)

### Inferences
- Default design for both platforms: bake `rclone` (or `aws-cli`) into the image, pass `RCLONE_CONFIG_R2_*` / `AWS_*` as env vars (`--env` on RunPod, `-e` / account env vars on Vast), `rclone copy r2:bucket/dataset /workspace/data` at start and `rclone copy runs r2:bucket/runs` at end, then self-destruct. No documented R2 compatibility with either built-in sync, so I would not depend on it.
- Use a bucket-scoped R2 token (read dataset, write runs prefix); on Vast community hosts the env var is readable by the host operator, so credentials should be minimally scoped and revocable.

### Gaps
- Whether Vast's S3 cloud connection accepts a custom endpoint (and therefore R2) is undocumented; I did not test it. Same for RunPod's S3 option (it asks for an AWS region).
- No documented rate or throughput for Cloud Sync on either platform.

## 6. RunPod Serverless for batch training jobs

### Takeaway
Technically possible within limits (execution timeout configurable up to 7 days; queue-based endpoints are described as suited to "batch processing, and long-running jobs"), but it is built for inference workers: you package a handler, pay flex per-second rates that are roughly 2-3x the equivalent Pod rate, and pay for cold start. For a single user running scripted YOLO training, Pods are simpler and cheaper; I found no RunPod doc recommending Serverless for training.

### Cited Findings
- [DOC] Queue-based endpoints: "built-in queueing system with guaranteed execution and automatic retries. Ideal for async tasks, batch processing, and long-running jobs. Implemented using handler functions"; load-balancing endpoints are for low-latency REST — [endpoint settings](https://docs.runpod.io/serverless/endpoints/endpoint-configurations.md)
- [DOC] Execution timeout: "Maximum duration for a single job. When exceeded, the job fails and the worker stops ... Range: 5s to 7 days"; console default 600 s, REST v2 default 300000 ms (5 min), per-request override via `executionTimeout` in the job policy. Job TTL default 24 h (10 s-7 d), counts queue time and is a hard limit. Initialization timeout default 420 s via `RUNPOD_INIT_TIMEOUT` (workers billed while initializing). Idle timeout default 5 s (console) / 10 s (REST v2) — [endpoint settings](https://docs.runpod.io/serverless/endpoints/endpoint-configurations.md)
- [DOC] Billing: per second "from when a worker starts until it fully stops, rounded up to the nearest second"; phases cold start (billed), execution, idle wait; image pull and cached-model download normally happen while scaled down and are not billed (but are billed if the image is not yet on the host); flex workers scale to zero; container disk about $0.10/GB/month, network volume $0.07/GB/month; $80/hour default spend limit — [Serverless pricing](https://docs.runpod.io/serverless/pricing.md), [workers overview (llms-full)](https://docs.runpod.io/llms-full.txt)
- [DOC] Flex GPU pools and per-second price: A4000/A4500/RTX 4000 (16 GB) $0.00016; L4/A5000/3090 (24 GB) $0.00019; 4090 PRO (24 GB) $0.00031; A6000/A40 $0.00034; L40/L40S/6000 Ada $0.00053 — [endpoint settings](https://docs.runpod.io/serverless/endpoints/endpoint-configurations.md). Serverless selects GPU pools, not an exact consumer card such as 3070/3080.
- [DOC] Cold-start reduction: FlashBoot (OFF / FLASHBOOT / PRIORITY_FLASHBOOT in v2), cached models, workers start "from cached container images"; no numeric cold-start times in the pages I read — [endpoint settings](https://docs.runpod.io/serverless/endpoints/endpoint-configurations.md), [migrate from v1](https://docs.runpod.io/api-reference-v2/migrate-from-v1.md)
- [DOC] Serverless storage: container disk is temporary; network volumes and external S3-compatible storage available — [Serverless storage](https://docs.runpod.io/serverless/storage/overview.md)

### Inferences
- Computed rate comparison: 3090-class flex $0.00019/s = $0.684/h vs Pod Community 3090 $0.22/h (about 3.1x) and Secure $0.50/h (about 1.4x); 4090 PRO flex $0.00031/s = $1.116/h vs Pod Community $0.34 (about 3.3x) and Secure $0.89 (about 1.25x).
- Serverless gives automatic worker teardown after a job (no self-destruct code, no forgotten pods), which is the main benefit for the "billing must stop" requirement, but a job that exceeds the execution timeout is killed and failed, and the training code would need a handler wrapper plus the 24 h/7 d TTL caveats. A fire-and-forget Pod with self-terminate gets the same cost safety more cheaply but needs the watchdog.

### Gaps
- No RunPod doc or user report found about running training on Serverless (checked docs index and overview; "training" and "fine-tuning" had no hits in the Serverless overview).
- No measured cold-start numbers for non-LLM images; payload-size limits for job inputs/outputs not extracted (relevant to returning model weights; use R2 upload instead).
